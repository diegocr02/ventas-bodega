# D0 — Documento de Definición del Proyecto

## Minimarket Bodega — Sistema de Ventas y Control de Stock

---

## 1. Problema

El cajero del minimarket de barrio en San Vicente de Cañete registra las ventas en un cuaderno y controla el stock mirando los estantes, lo que le impide conocer el total vendido al cierre del día y provoca quiebres de stock en productos de alta rotación porque nadie detecta a tiempo que se están agotando.

---

## 2. Usuarios y responsabilidades

| Usuario | Rol | Qué hace en el sistema |
|---------|-----|------------------------|
| Cajero  | Único usuario operativo | Registra productos, consulta el listado con alertas de stock bajo, registra ventas y consulta las ventas del día. |

> No existe ningún otro perfil de usuario en el alcance de este proyecto.

---

## 3. Proceso actual y su dificultad

**Proceso actual:**
- Las ventas se anotan manualmente en un cuaderno, una por una.
- El nivel de stock se estima visualmente mirando los estantes.

**Dificultades identificadas:**
- No se conoce el monto total vendido al cierre del día.
- Los quiebres de stock ocurren porque el cajero no detecta oportunamente que un producto está llegando a su nivel mínimo.
- No existe descuento automático de stock al momento de cada venta.

---

## 4. Requisitos Funcionales

**RF1 — Gestión de productos**
El sistema debe permitir registrar un producto con los siguientes datos: código único, nombre, categoría, precio de venta, stock actual y stock mínimo.

**RF2 — Listado de productos con alerta de stock bajo**
El sistema debe listar todos los productos y resaltar visualmente aquellos cuyo stock actual sea igual o menor a su stock mínimo.

**RF3 — Registro de venta**
El sistema debe permitir al cajero seleccionar un producto e indicar la cantidad vendida. El sistema tomará el precio de venta vigente del producto, calculará el total, registrará la fecha y hora de la transacción, y descontará la cantidad del stock actual. La venta y el descuento de stock ocurren de forma atómica: si alguno falla, no se aplica ninguno.

**RF4 — Listado de ventas del día**
El sistema debe listar todas las ventas registradas en el día en curso y mostrar el total acumulado vendido en el día.

---

## 5. Requisitos No Funcionales

**RNF1 — Integridad de datos**
La operación de registro de venta y descuento de stock debe ejecutarse dentro de una transacción de base de datos; si cualquier parte falla, toda la operación se revierte.

**RNF2 — Persistencia**
Los datos de productos y ventas deben persistir en una base de datos relacional entre sesiones.

**RNF3 — Usabilidad mínima**
Los productos con stock bajo deben diferenciarse visualmente del resto en el listado (p. ej. color de fila o ícono de alerta) para que el cajero los identifique de un vistazo.

**RNF4 — Consultas parametrizadas**
Toda interacción con la base de datos debe realizarse mediante PDO con sentencias preparadas; queda prohibida la concatenación directa de valores de usuario en cadenas SQL.

**RNF5 — Credenciales fuera del repositorio**
Las credenciales de conexión a la base de datos deben almacenarse en un archivo `.env` que no se incluye en el repositorio de control de versiones.

**RNF6 — Escape de salida en vistas**
Toda cadena proveniente de la base de datos o de la entrada del usuario que se muestre en el HTML debe escaparse con `htmlspecialchars` antes de ser enviada al navegador.

**RNF7 — Validación en el servidor**
Todos los datos enviados por el cajero a través de formularios deben validarse en el servidor antes de procesarse o persistirse.

---

## 6. Reglas de Negocio

**RN1 — Cantidad vendida positiva**
La cantidad indicada en una venta debe ser mayor que cero.

**RN2 — Stock suficiente**
No se puede registrar una venta si la cantidad solicitada supera el stock actual del producto. El sistema debe rechazar la operación e informar al cajero.

**RN3 — Precio de venta no negativo**
El precio de venta de un producto no puede ser un valor negativo.

**RN4 — Código de producto único**
No pueden existir dos productos con el mismo código en el sistema.

**RN5 — Atomicidad de venta y descuento de stock**
El registro de la venta y el descuento del stock ocurren juntos dentro de una misma transacción. Si alguno de los dos pasos falla, ninguno se aplica.

---

## 7. Fuera de Alcance

Los siguientes elementos quedan explícitamente excluidos de este proyecto:

- **Autenticación y control de acceso:** No existe login, contraseñas ni gestión de sesiones.
- **Roles de usuario:** No se contempla ningún sistema de roles ni permisos diferenciados.
- **Gestión de clientes:** No se registran datos del comprador.
- **Emisión de comprobantes:** No se generan boletas ni tickets de venta.
- **Facturación electrónica:** No se integra con SUNAT ni con ningún proveedor de comprobantes electrónicos.
- **Módulo de compras / reposición:** No se registran ingresos de mercadería ni proveedores.
- **Reportes históricos:** No se contempla ningún reporte más allá del listado de ventas del día en curso.
- **Múltiples sucursales o usuarios concurrentes avanzados:** La aplicación es para un único punto de venta.
- **Gestión de categorías dinámica:** Las categorías se manejan como texto libre en el producto; no existe un catálogo de categorías administrable.
- **Agentes conversacionales o asistentes de IA:** No se integra ningún chatbot ni modelo de lenguaje.
- **Despliegue público:** La aplicación no está diseñada para ser expuesta en internet ni en servidores en la nube.

---

## 8. Supuestos

| # | Supuesto |
|---|----------|
| S1 | SUPUESTO: La aplicación corre en un servidor local (XAMPP) accesible solo desde la red interna del minimarket. |
| S2 | SUPUESTO: Los precios de venta se gestionan directamente en el formulario de productos; no existen listas de precios ni descuentos. |
| S3 | SUPUESTO: El «día en curso» para el listado de ventas (RF4) se determina por la fecha del servidor. |
| S4 | SUPUESTO: La cantidad vendida se trata como un número entero (unidades completas); no se admiten fracciones. |
